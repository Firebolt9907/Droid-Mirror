# Optional automatic screen unlock

On Android open **DroidMirror → Optional features and recovery → Automatic unlock / saved PIN**.
Confirm the current device credential, enter and confirm the numeric screen-lock
PIN (4–16 digits), then save. This is separate from the Mac Bluetooth pairing code.
The same screen replaces or removes the saved PIN; it never reveals the old value.
Saving enables automatic entry for future authenticated Bluetooth/hybrid sessions
and authorized ADB sessions. The last foreground app remains selected; Android
shows home if there is no app to resume. No Home key is injected.

The app stores only AES-256-GCM ciphertext and its random IV in private preferences.
The non-exportable key is generated by Android Keystore. App backups are disabled.
The editor requires device credential confirmation, blocks screenshots/recents
previews, disables autofill and field-state saving, and clears fields on exit.
The key intentionally permits use while locked, so a trusted paired Mac or an
authorized ADB computer can unlock the phone without local confirmation. Hardware
backing depends on the device. Root or a compromised app process can still observe
the decrypted PIN. This feature does not bypass Android credential verification.

A PIN is decrypted only for startup and handed over phone-local Binder to the
privileged input process. Mutable PIN arrays are cleared afterward. There are no
PIN command-line arguments, clipboard transfers, Bluetooth/ADB wire messages to
the computer, or PIN logs. Before handing over a PIN, the app synchronously persists
a 15-second cooldown timestamp. Confirmed keyguard dismissal clears it through a
phone-local callback. A later encoder or transport failure therefore does not pause
a PIN that already unlocked the phone. A failure, crash or interrupted unlock
prevents rapid reconnect attempts with a stale PIN. During the cooldown, normal
mirroring connects without reading or entering the PIN, so manual unlock remains
available. After expiry, only a new user-initiated connection can try the PIN again;
there is no background retry loop. Legacy indefinite pauses automatically expire.
Saving a replacement PIN clears the cooldown. Change the saved value whenever the
phone PIN changes.

Bluetooth startup keeps the existing authenticated transport and ownership checks,
rejects a phone already in use, acquires display recovery before waking, and warms the capture/encoder in parallel with PIN entry. Codec metadata may
reach the Mac decoder immediately, but an output gate drops captured pixel frames
until unlock succeeds. The gate rejects queued pre-unlock timestamps and requests
a fresh keyframe before releasing video. Physical screen-off follows the
existing user preference. ADB uses a DUMP-protected companion service and a one-shot
Binder handshake in parallel with encoder preparation; its PIN entry can be visible on the
physical phone until the client turns the panel off. Both paths open Android's
credential bouncer, clear partial input, enter digits once, submit only if still
locked, and require keyguard dismissal before video begins. Keyguard state is
checked before every key to stop if another unlock occurs. Preparation sends SPACE
twice, 700 ms apart, before clearing or entering credentials. Unlike MENU, SPACE
does not depend on the lock-screen MENU-enable configuration. This also handles
an already-on lock screen or an expanded lock-screen notification shade: the first key can
be consumed by the asynchronous wake/AOD transition. This is a bounded settling
window, not a guarantee of readiness on every OEM. After the single PIN submission,
keyguard dismissal has a four-second deadline; no credentials are retried. Normal Android unlock
sounds/haptics follow the phone settings. OEM credential screens, lockout timers,
SIM locks, and managed-device restrictions can prevent automatic entry; there is
no claim of universal lock-screen compatibility.

## Verification

Run `bash Native/test-pin-unlock.sh` for leading zeros, validation, already-unlocked
phones, explicit and automatic confirmation, early biometric dismissal, one failed
attempt and bounded timeout, a wake transition that consumes the first SPACE,
an awake lock screen with MENU disabled, slow keyguard dismissal, and biometric dismissal during preparation. Build the companion with `./gradlew assembleDebug`
and rebuild the bundled scrcpy server for ADB support.

On a test phone, verify save/replace/remove, credential cancellation, rotation and
backgrounding (no retained field values), screenshots blocked, and no plaintext
PIN in preferences/logs. Lock with an app foreground, start Bluetooth and ADB
sessions, and verify the first visible video is that app. Repeat from home, with
screen-off enabled/disabled, with a wrong PIN, after a crash during preparation,
after reboot/first unlock, and after changing the system PIN. A wrong PIN must
fail without exposing its entry frames. The next connection must stream normally
for manual unlock while automatic entry cools down across app restarts. Reconnecting after 15 seconds
can try the PIN again.
The Mac keeps the loading view over transient fully black frames and starts the
entrance animation only after inspectable nonblack content has remained on the video surface
for 150 ms. A black or uninspectable frame resets that confirmation period, so a
startup flash cannot consume the animation. Static content is confirmed by the
render loop even if no new frames arrive. The loading overlay stays above SDL’s newly created Metal surface during warmup,
preventing empty-drawable flashes. A genuinely black/protected app receives a bounded
1.5-second fallback without the entrance animation.

Before installing an update, end any active mirror session gracefully, then replace
the app/server and reconnect. An independent startup timer reapplies panel-off during Android’s asynchronous wake and PIN injection; it does not extend the recovery deadline. The Shizuku service version is bumped for the new
capture signature; replacing components during an active session is not seamless.

## Require Touch ID on the Mac

In Mac Settings → Phone unlock, enable **Require Touch ID to unlock phone**.
The default is off. The prompt appears only after the phone connection is
confirmed, not when you click Connect. Over Bluetooth that means Android accepted
the Classic session and the per-session BLE channel authenticated. Android
checks for local use (awake and unlocked) before starting BLE, so a phone in use
ends the session with `EVENT PHONE_IN_USE` and no prompt. The helper
then emits `EVENT UNLOCK_DECISION_NEEDED` and holds the first capture record,
including heartbeats, until the app answers `UNLOCK_DECISION 0|1` on stdin.
Capture and video wait for the answer. With no answer within 30 seconds, the
helper falls back to manual unlock. The prompt itself closes after 25 seconds.
Android waits up to 45 seconds after BLE starts for that first record. Over ADB,
the prompt appears after adb reached the phone and the phone-in-use check passed.
The second byte of the start gate carries the answer to the client, which passes
it to the server. Without that byte, the fail-closed launch default stands.
For each new mirror session, the host evaluates a fresh
`LAContext` with `.deviceOwnerAuthenticationWithBiometrics`, zero reuse duration,
and a hidden fallback button. There is no Mac password or Apple Watch fallback.
[Apple documents this biometric-only policy](https://developer.apple.com/documentation/localauthentication/lapolicy/deviceownerauthenticationwithbiometrics).
Cancel (**Unlock manually**), failed authentication, lockout, or unavailable
biometrics starts the mirror on the normal Android lock screen without reading
or submitting the saved PIN and without consuming its cooldown. Manual phone
input and the existing Mac PIN keypad remain available. Stopping the connection
invalidates the prompt; a late result cannot start a cancelled connection.
Success is scoped to the selected device/transport and next capture startup;
reconnects prompt again. This setting cannot change during startup or an active mirror.

The option cannot be newly enabled unless Touch ID is available and enrolled.
An already enabled requirement never silently downgrades when Touch ID disappears.
In lid-closed/clamshell mode, use a supported external Touch ID keyboard or open
the lid; otherwise cancel and unlock Android manually. No sensor means no
biometric authorization, including after enrollment changes or biometric lockout.
There is no separate in-session saved-PIN action: after cancelling, use manual
unlock, or stop and reconnect to request Touch ID again. This keeps one bounded
PIN attempt per capture and preserves cooldown behavior.

### Binding and threat model

The PIN remains solely on Android, encrypted by Android Keystore; the Mac has no
PIN item to protect with Keychain `.biometryCurrentSet`. Existing Mac pairing
keys remain transport credentials, not proof of biometric authentication. The
host gates both startup callers in `MirrorModel.start`: Bluetooth (including USB
accessory/direct IP video upgrades) and direct ADB. Hybrid video/audio upgrades
only replace transport and do not request another PIN. Manual keyboard/keypad
entry is deliberately allowed and requires knowledge of the Android credential.

Bluetooth sends a standalone `0x71 / length 1 / allow 0-or-1` decision as the first
encrypted capture input record. Only that first sequence-checked record can
authorize PIN retrieval; a missing/legacy decision defaults to manual unlock and
later grants cannot upgrade it. It is authenticated under the fresh capture
nonce-derived key; old-session ciphertext, tampering and sequence replay fail
existing crypto checks. ADB passes an explicit default-false server option through
its verified, owner-bound Binder handshake, retaining its one-shot PIN guard.
Neither path changes Android authentication, sequence validation or cooldown.
Use matching updated Mac client/helper, scrcpy server and Android companion;
Bluetooth rejects companions lacking the unlock-decision capability before sending
any capture input; ADB rejects a legacy PIN handoff when authorization was denied.
Older components may fail to connect rather than offer a safe manual-only session.
An older Android companion still waits only 15 seconds, BLE setup included, so
answer Touch ID quickly or update the companion. End sessions before updating components.

This is a local convenience/privacy gate against unattended use of the normal
Mac app, not remote biometric attestation. A compromised Mac/user account can
change preferences, forge an allow decision using its pairing key, or use
independently authorized ADB; root/compromised Android can observe the PIN.
Enforcing biometric presence against a malicious paired computer would require
an Android-enforced policy and a separately protected signing credential.

Run `bash Native/test-touch-id-unlock.sh` for first-record approval/denial,
malformed/legacy input, late-grant rejection, cross-session isolation, crypto
replay/tamper rejection, LA wrapper typecheck, BLE transport syntax checking,
and native encrypted allow/deny records plus legacy capability rejection.
Also run `bash Native/test-pin-unlock.sh`. Device testing still needs both
