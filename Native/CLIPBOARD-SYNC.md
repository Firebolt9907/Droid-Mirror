# BLE clipboard mirroring

Enable **DroidMirror → Mirror Clipboard over Bluetooth** (or **Settings → Clipboard**) on the Mac. It is off by default. Install builds containing this
feature on both devices, retain the existing pairing, enable the Android background
bridge, and authorize Shizuku. Clipboard sync works without an open mirror window
or an IP network. Notification-listener permission is not required for clipboard.
Settings reports whether clipboard mirroring is ready, waiting for Bluetooth/Shizuku,
or paused because the phone is locked.

Newly copied, nonempty plain text and individual files are mirrored in both directions.
Copy one regular file at a time; folders, file selections, rich formatting, raw image
pasteboard data and clipboard history are not transferred. An image copied as a file
is supported. Each file must be **strictly less than 5 MB (5,000,000 bytes)**; a file
of exactly 5,000,000 bytes is rejected. Empty files are supported. Android source
files must be readable `content://` clipboard URIs with a known size; destination
apps must support pasting content URIs. Files are not automatically opened.
Text is limited to 4096 UTF-8 bytes;
JSON escaping may lower this limit so the encrypted envelope fits the existing
8192-byte BLE message bound. Oversized text is skipped rather than truncated.
Poll intervals are 500 ms on the Mac and 750 ms on Android, plus BLE transfer time.
Rapid intermediate clipboard changes between polls may be missed.

The receiver uses the existing mutually authenticated AES-GCM BLE connection,
sequence checks, and fragmentation. The Android service advertises a capability
before the Mac sends clipboard commands; older companions retain notifications.
Only one authenticated Mac at a time may subscribe to Android clipboard events.
Disabling sync, disconnecting, stopping the bridge or revoking pairing tears down
the clipboard subscription. Clipboard commands do not own or restart capture.
A separate non-daemon Shizuku user service accesses Android's shell clipboard;
it does not replace the display-recovery daemon or acquire a display lease.

Neither device uploads its pre-existing clipboard when subscribing/reconnecting.
Remote writes are suppressed from echoing back. A local Mac copy made since the
last poll takes priority over an arriving phone update. There is no durable retry
queue; a failed/offline copy must be copied again after reconnection. Android
clipboard reads and writes pause while locked; the first readable value after
unlock is used as a baseline. Sensitive Android clips and Mac concealed, transient,
and autogenerated pasteboard types are skipped. Unmarked secrets are ordinary
text and will sync when enabled. Contents are never logged. Text is not persisted;
received files are stored in a private clipboard cache so destination apps can paste
them. Each device keeps at most ten received files (under 50 MB); older entries are
removed when another file arrives, and the OS may evict cache data sooner. Android
exposes completed files through a read-only content provider with URI permissions.

Files use a separately negotiated `clipboardFiles` capability, enabled in the
clipboard subscription. Older companions continue to support text sync. File events
(`clipboardFileBegin`, `clipboardFileChunk`, `clipboardFileAck`, `clipboardFileCancel`)
use the existing authenticated session and sequence checks. Each chunk contains up
to 3072 bytes encoded as URL-safe Base64, avoiding JSON slash expansion within the
8192-byte encrypted message limit. Only one chunk is sent before its matching byte
offset is acknowledged. Both sides validate declared sizes, actual byte counts,
filenames and chunk offsets. Sources are snapshotted with bounded reads. A newer local
copy, lock, disconnect or opt-out discards pending transfers; stalled transfers expire
after 60 seconds without progress. Partial files are never placed on the clipboard.
Large transfers over Bluetooth can take time; there is no network upload or fallback.

## Validation

- `bash Native/test-clipboard-sync.sh`: isolated named Mac pasteboard (requires
  access to the macOS pasteboard service), opt-in, new copies, echo suppression,
  local conflicts, privacy markers, limits, reconnects, old-peer compatibility;
  file send/receive, empty files, exact 5 MB rejection, 4,999,999-byte acceptance,
  invalid names/offsets and cancellation. The JVM harness exercises the production
  Android file-transfer state machine with a fake bridge and temporary cache.
- `bash Native/test-integrated-ble.sh`: actual Swift/Kotlin authentication,
  tamper/replay rejection and encrypted clipboard envelope bounds, including
  maximum file chunks containing all-zero and all-0xff bytes.
- Compile the BLE library/helper with the source list in `build-app.sh` and Android
  with `compileDebugKotlin compileDebugJavaWithJavac`.

The live Pixel check passed in both directions with synthetic text and emoji,
without an open mirror session. The probe preserved both original clipboards in
memory and restored them after temporarily pausing sync. Reproduce with
`bash Native/test-clipboard-live.sh SERIAL` after compiling the debug companion;
keep the phone unlocked, clipboard sync enabled, and the Mac receiver running.
No clipboard contents are printed by the probe.

The phone's simultaneous Classic and LE GATT links caused the original handshake
indications to be acknowledged on the wrong transport. The notification/clipboard
server now explicitly requests LE using Android's transport-selecting platform
method. Reflection access was verified on this Pixel; other vendors/versions need
validation. Authentication, encryption and sequence checks remain unchanged.

Physical-device file-transfer validation is still required (the JVM bridge is simulated): both directions with the mirror
closed and open, Unicode, lock/unlock, Shizuku stop/restart, Bluetooth reconnect,
and disabling sync. Vendor restrictions on shell clipboard access may vary.
End active mirror sessions gracefully before installing either updated component;
this change does not make replacement during an active session seamless.
