# Synthetic BLE throughput benchmark

This explicit Mac-to-phone test generates a known byte pattern, checks the exact
byte count and SHA-256 on Android, and discards the data. It never accesses either
clipboard, Shizuku or file providers. The phone may remain locked with its screen
off; clipboard sync's unlock requirement remains unchanged.

Run after the background receiver has authenticated the paired phone:

```sh
swift Native/run-ble-bulk-test.swift --transport iroh --bytes 1048576 --window 0
swift Native/run-ble-bulk-test.swift --transport l2cap --bytes 1048576 --window 0
swift Native/run-ble-bulk-test.swift --transport l2cap --bytes 1048576 --window 32
swift Native/run-ble-bulk-test.swift --transport gatt --bytes 1048576 --window 0
swift Native/run-ble-bulk-test.swift --transport gatt --bytes 1048576 --window 32
```

`window 0` continuously fills a bounded queue without intermediate application
ACKs. `1`, `8` and `32` test cumulative ACK pacing using 3072-byte records. The GATT
variant uses a dedicated WRITE_WITHOUT_RESPONSE characteristic and Core Bluetooth
backpressure; it does not enable streaming on the text/control characteristic.
All variants use the same encrypted record format and generated pattern. The
iroh variant runs over direct IP with BLE bootstrap, using a benchmark-derived key
separate from real clipboard traffic. It requires a reachable LAN/VPN route. Its
local listener is exclusive with the real clipboard iroh lane, so run it when no
clipboard iroh lane is active (locking the phone closes that lane). A conflict
fails setup; it does not replace an active clipboard lane.

Each command prints one JSON result. `receiverKBps` is decimal KB/s, equivalent to
bytes divided by milliseconds. `receiverMs` includes the initial readiness ACK,
data transfer and validation; `totalMs` also includes negotiation/setup.
`lockedStart`/`lockedEnd` report keyguard lock. A successful run requires a matching
count and SHA-256; the flags report device state rather than bypassing a failure.
`diagnostics` reports local wire bytes, pending queue and stream backpressure.

One test is active per authenticated peer/session. Bytes are bounded to 1..4,000,000
and runtime to 180 seconds. A temporary PARTIAL_WAKE_LOCK keeps only the CPU
available during the test, without keeping the display on, and is released on
completion, cancellation, timeout, stop, disconnect or reauthentication. HIGH
connection priority is active only while data is in flight and returns to BALANCED.
No synthetic traffic, heartbeat or polling continues after the explicit test.

Tests derive a separate HMAC-SHA256 master from the pairing key using the context
`DroidMirror synthetic BLE benchmark v1`, then derive directional AEAD record keys
from a fresh offer token. Record sequences are independent of both clipboard and
control traffic. Test records cannot authenticate as clipboard records. Offers,
results and requests travel through the authenticated, sequenced control channel.
Raw GATT test data is accepted only from the current authenticated test owner. The
receiver never hands these records to ClipboardSyncClient or ClipboardFileTransfer.

The local request/result notifications are `app.droidmirror.bulkTest` and
`app.droidmirror.bulkTestResult`, correlated by UUID. The runner and receiver must
run as the same macOS user. No test runs automatically on connection or unlock.

Verification:

```sh
bash Native/test-ble-bulk-benchmark.sh
# Compile Android first, then run (the cross-platform test uses its class output):
bash Native/test-clipboard-bulk.sh
bash Native/test-ble-session.sh
```

Packet-level HCI traces remain a separate diagnostic. These benchmark counters do
not themselves prove packets per connection event or retransmission counts.

## Hardware observations (2026-10-30)

A Mac-to-phone L2CAP run transferred 262,144 generated bytes with window 32 in
8,501 ms (30.84 KB/s, approximately 0.247 Mbps). SHA-256 matched and both
`lockedStart` and `lockedEnd` were true. Setup-inclusive time was 8,833 ms.
Local counters reported 266,567 transmitted wire bytes, a largest accepted stream
write of 8,192 bytes and 95 backpressure observations. These are host observations,
not radio packet counts.

A continuous/window-0 run of the same size took 10,779 ms (24.32 KB/s), but the
phone was unlocked. This is not a controlled comparison and does not demonstrate
a benefit from removing application ACKs. Neither result approaches the raw 2M
PHY rate.

The GATT comparison has not produced a valid throughput result. An installed run
sent its 58-byte hello, then remained backpressured with 149 bytes queued before
the BLE session ended. Subsequently the ordinary connection was scanning even
with the benchmark stopped, and wireless ADB was offline. Do not interpret these
failed runs as successful measurements or as a proven hardware throughput limit.
Repeat only after the normal authenticated connection is stable. HCI capture is
still needed to distinguish link scheduling, retransmissions and credit stalls.

A subsequent Mac scheduling change gives the bounded benchmark burst a turn
before ordinary control sends consume newly available Core Bluetooth credits.
It was compiled, regression-tested and installed, but a post-install measurement
could not start while the receiver was scanning. Its hardware effect is unverified.

A later direct-IP iroh run transferred the same 262,144 bytes in 437 ms
(599.87 KB/s, approximately 4.80 Mbps), with matching SHA-256 and both lock flags
true. Setup-inclusive time was 4,589 ms: approximately 4.15 seconds of cold setup
and acknowledgement overhead before the sender's measured data interval. This
is one hardware observation, not a guaranteed setup latency or a warm-connection
measurement. It validates the independent IP lane, while the full parallel race
is additionally covered by the production arbitration tests.
